# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

OAuth Diagnostic Tool — a cross-platform desktop app for managing and interacting with OAuth servers locally. Built with **Tauri 2** (Rust backend) and a **TypeScript + React 19** frontend bundled with **Vite**.

## Build & Dev Commands

```bash
# Install frontend dependencies (needed before the first dev/build, and after changing ui/package.json or the lockfile)
cd ui && npm install

# Run the app in development mode (starts the Vite dev server on port 5173 via beforeDevCommand)
cargo tauri dev

# Build for production (runs `npm run build` in ui/ via beforeBuildCommand)
cargo tauri build

# Typecheck the frontend
cd ui && npm run typecheck

# Build the frontend only (typecheck + vite build into ui/dist/)
cd ui && npm run build

# Run frontend unit tests (Vitest)
cd ui && npm test

# Lint the Rust backend (CI runs this with -D warnings)
cd src-tauri && cargo clippy --all-targets -- -D warnings

# Run Rust tests (includes the bindings_are_current check)
cd src-tauri && cargo test

# Regenerate ui/src/bindings.ts after changing a command or event type
cd src-tauri && UPDATE_BINDINGS=1 cargo test bindings_are_current

# Run landing page unit tests (node:test, no dependencies)
cd site && npm test

# Preview the landing page with its Cloudflare Pages headers
cd site && npx wrangler pages dev public --port 8788
```

Requirements: Node.js 24 LTS with npm, Rust 1.85+ (`rust-version` in `Cargo.toml`), and `tauri-cli` 2.12+ (`cargo install tauri-cli --version "^2.12" --locked`).

CI (`.github/workflows/ci.yml`) runs two jobs on pushes to `main` and on PRs: `rust` (macOS: clippy + `cargo test`) and `frontend` (Ubuntu: `npm ci`, typecheck, `npm test`, `npm run build`). Clippy uses `--all-targets -D warnings`, so test code must be clippy-clean too. The Rust job runs `mkdir -p ui/dist` first because `tauri::generate_context!` needs the frontend dist directory to exist at compile time.

`.github/workflows/deploy-site.yml` is started manually. It runs the `site/` tests and deploys `site/public/` to the `oauth-diag-tool` Cloudflare Pages project with Wrangler, using the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets. A run from `main` updates production; a run from another branch creates a preview deployment.

## Testing Conventions

- Rust tests are inline `#[cfg(test)] mod tests` blocks at the bottom of each module (the modules are private in `lib.rs`, so inline tests can reach private helpers). DB-backed tests get an in-memory SQLite connection from `db::open_test_connection()`, which runs the full schema init.
- Migration upgrade tests hand-build the historical base schema — the fresh-install `SCHEMA` already contains all migrated columns, so running migrations against it would fail with "duplicate column".
- `lib.rs` has a `bindings_are_current` test that fails when `ui/src/bindings.ts` does not match what the Rust command and event definitions produce. It is the check that keeps the Rust↔TypeScript contract in sync.
- Frontend tests are Vitest `*.test.ts` files next to the modules they cover in `ui/src/lib/`. Vitest runs in the `node` environment (`vite.config.ts`), so tests target the pure modules rather than rendered components. Put logic that needs coverage in `lib/`, not in components or hooks.

## Architecture

**Two-part structure:**

- `src-tauri/` — Rust backend using Tauri 2. Entry point is `main.rs` which calls `lib.rs` for Tauri Builder setup.
  - `src-tauri/src/lib.rs` — Tauri command definitions and app setup. Manages three pieces of state: `Arc<Mutex<Connection>>` (DB), `Mutex<RunningServers>` (server tasks), and `PendingAuthorizations` (in-flight auth code flows; a second authorize for the same config while one is in flight is rejected). `check_local_target` runs before authorize, refresh, resource and MCP requests: a refused loopback port (naming the stopped configured server) or a metadata-document client ID the running server will refuse fails immediately, before a browser opens. Delegates logic to `auth_server`, `auth_client`, `discovery`, and `db` modules (`cimd` and `dcr` are pure helpers used by `oauth_server`). `create_client_config`/`update_client_config` take a single `config: ClientConfigInput` struct argument (the generated bindings pass `{ config }`), and `update_server_settings` takes `settings: ServerSettingsInput`. Commands are registered through `specta_builder()` (tauri-specta): every command needs `#[tauri::command]` + `#[specta::specta]` and an entry in `collect_commands!`, and frontend-facing DTOs derive `specta::Type`. Debug runs export TypeScript bindings to `ui/src/bindings.ts`; the `bindings_are_current` test fails when that file is stale (regenerate with `UPDATE_BINDINGS=1 cargo test bindings_are_current`). `ResourceAccessInfo` is a typed `tauri_specta::Event` named `resource-access` (carries the token's `username`); `ServerUsersChanged` is named `server-users-changed` and fires when a user registers on the login page; `ServerClientsChanged` (`server-clients-changed`) fires when a client registers through `/register`; `ClientMetadataFetched` (`client-metadata-fetched`: server id, client ID URL, ok, message, client name, timestamp) fires for every metadata document fetch, not for cache hits.
  - `src-tauri/src/db.rs` — SQLite init with versioned migrations (`LATEST_VERSION` is derived from the last `MIGRATIONS` entry; version 2 was never shipped — keep the numbering gap). `init()` opens the file; `init_connection(&Connection)` does the PRAGMA/schema/migration work on any connection (tests feed it an in-memory one). Tables: `server_configs` (incl. `user_based`, `cimd_enabled` default 1, `dcr_enabled` default 1, `cimd_allow_http` column default 0 but set to 1 by `auth_server::create` for new servers, `mcp_enabled` default 0, `public_url` default '' (migration 18)), `auth_server_clients` (incl. `client_name`, `redirect_uris` JSON text, `token_endpoint_auth_method`, `registration` of `manual` or `dynamic`; public clients store an empty `client_secret`) and `server_users` (both FK cascade delete), `oauth_client_configs` (incl. `resource_url`, empty meaning no protected resource), `schema_version`. `PRAGMA foreign_keys = ON`. `oauth_client_configs` carries `registration_mode` (`preregistered`/`cimd`/`dcr`), `token_auth_method` (a DCR client's registered method) and `serve_client_metadata` (migration 15), plus `mcp_url` and `token_for_mcp` (migration 17).
  - `src-tauri/src/auth_server.rs` — Server config CRUD and lifecycle. `start()` binds the listener (127.0.0.1 only) *before* spawning the task so port conflicts are returned as errors instead of leaving a phantom "running" server. `extract_port()` is strict and returns `Result`; `get_all()` sends derived `port` and `issuerUrl` (the effective issuer from `issuer_url(port, public_url)`: the public URL when set, else `http://localhost:<port>`) to the frontend so the UI never parses URLs. Also owns server users (`add_user`, `update_user`, `delete_user`, `verify_user`, `lookup_user_data`); usernames are stored trimmed and `user_data` defaults to `example data for user <username>`. Generates URL-safe client IDs (24 chars) and secrets (48 chars); `add_dynamic_client` stores a `/register` client (no secret for auth method `none`). `create` requires a non-blank name. `update_settings` takes a `ServerSettingsInput` (redirect override, expiries, `user_based`, `cimd_enabled`, `dcr_enabled`, `cimd_allow_http`, `mcp_enabled`, `public_url`) and rejects an override that is not an absolute http(s) URL or an expiry outside 0 to 10 years; `normalize_public_url` accepts only an http(s) origin (no path, query, fragment or credentials, since RFC 8414/9728 well-known URLs put the well-known segment before the path) and stores its canonical serialization without the trailing slash. `start()` copies the settings into `ServerState` and `RunningServer.applied`; with a public URL, `ServerState.issuer_url` is that URL and `token_url` is `advertised_token_url()` (`{public_url}/token`), while the listener still binds 127.0.0.1. `get_all` compares `applied` with the saved settings to report `restart_required` and `mcp_active`. `restart()` is stop plus start. `local_cimd_problem()` explains why a running server will refuse a metadata-document client ID. Running servers are stopped on app close via `Drop`.
  - `src-tauri/src/oauth_server.rs` — Axum-based OAuth server. Routes: `GET /authorize` (consent page; all interpolated values are HTML-escaped via `html_escape`), `POST /authorize` (re-validates client_id and re-applies the redirect override server-side — hidden form fields are never trusted; redirect_uri must be absolute http(s)), `POST /token` (client_credentials, authorization_code, refresh_token grants; PKCE checks go through the pure `verify_pkce()`; JWT access tokens signed with per-server HMAC-SHA256 key), `GET /resource` (validates Bearer JWT incl. audience via the shared `authenticate_bearer()`, emits `resource-access` event (carrying the requested `path`, `/resource` or `/mcp`) to the frontend; the response is the claims plus `userData` read from the DB at request time, or only `username` and `userData` on user-based servers). The `ProtectedResource` enum (`Sample` = `/resource`, `Mcp` = `/mcp`) parameterises the resource identifier, the PRM URL and the `bearer_challenge()`. When `mcp_enabled` is on, `POST /mcp` (Streamable HTTP, JSON responses only; `GET`/`DELETE` give 405 after authentication, so an unauthenticated GET still gets the 401 challenge) serves the MCP endpoint: 404 when disabled, 403 for non-loopback `Origin`, 401 + challenge pointing at `/.well-known/oauth-protected-resource/mcp` (audience must be `{issuer}/mcp`), 400 for an unsupported `MCP-Protocol-Version` or unparsable JSON, and the root `/.well-known/oauth-protected-resource` then describes `/mcp` instead of `/resource`. When the server's `user_based` setting is on, `GET /authorize` renders a login page (sign in / deny / create user) instead of the consent page, `POST /authorize` accepts only `login`, `register` and `deny`, and auth codes, refresh tokens and JWTs (`username` claim) carry the username. `ServerState.issuer_url` is the effective issuer (the public URL when set): the AS metadata issuer and endpoints, both PRM documents, the `resource_metadata` challenge URL, the JWT `iss` and the expected audiences all derive from it, and the integration tests check each with the public URL on and off. `GET /.well-known/oauth-authorization-server` serves RFC 8414 authorization server metadata (no OIDC discovery; the server issues no ID tokens). `/.well-known/oauth-protected-resource/resource` (RFC 9728 path-insertion form) and `/.well-known/oauth-protected-resource` (root form) serve protected resource metadata for `{issuer}/resource` (`authorization_servers` is the issuer; no `scopes_supported`, matching the AS metadata). Every 401 from `/resource` carries `WWW-Authenticate: Bearer realm=..., resource_metadata="<path-insertion PRM URL>"`, plus an `error` param only when a token was presented and rejected (a missing or non-Bearer `Authorization` header gets no `error`, per RFC 6750); `bearer_challenge()` builds the header. Client kinds: manually added clients are confidential (any absolute http(s) redirect); DCR clients (`POST /register`, RFC 7591, 404 when `dcr_enabled` is off; `redirect_uris` validated by `dcr::validate_registration`, default auth method `client_secret_basic`, secret only for confidential methods, responds 201 with `Cache-Control: no-store`) have their registered `redirect_uris` enforced by exact match at `/authorize`; a `client_id` that is an https URL (http on loopback when `cimd_allow_http`) with a path and no fragment is a Client ID Metadata Document client (`cimd::classify_client_id`); an unusable client ID URL gets an HTML error page at `/authorize`. The document is fetched (5s timeout, no redirects, 5 KB cap), validated by the pure `cimd::validate_metadata` (client_id equals the URL, `redirect_uris` exact match, auth method absent or `none`, no `client_secret`), and cached per server in `ServerState.cimd_cache` (5 minutes, or `Cache-Control: max-age` up to 1 hour; `no-store` disables caching; only documents that pass `parse_metadata` are cached). `GET` and `POST /authorize` call `resolve_authorize_client`, which renders an HTML error page (never a redirect) for an invalid document, unregistered redirect URI, or a public client without `code_challenge`; consent and login pages show the client ID URL's host prominently plus the document's `client_name`, `client_uri` and `logo_uri` as escaped text. `redirect_url_override` is applied after validation: the client is checked against the `redirect_uri` it sent (the hidden form field carries that original value) and the override only changes where the code is sent. `authenticate_client` (async) returns an `AuthenticatedClient` with a `ClientKind` (`Confidential`, `Public`, `MetadataDocument`): confidential clients use `client_secret_post`/`client_secret_basic`, public and metadata-document clients authenticate by `client_id` alone, must present a `code_verifier` for a code issued with a `code_challenge` (`check_pkce`), may refresh with `client_id` alone, and get `unauthorized_client` for `client_credentials`. AS metadata (`build_metadata`) adds `client_id_metadata_document_supported` when CIMD is on, `registration_endpoint` when DCR is on, and `none` to `token_endpoint_auth_methods_supported`. `ServerState.app_handle` is `None` in tests, so events are skipped; integration tests serve the router and mock metadata documents on loopback ports. Auth codes are stored in-memory with a 10-minute TTL (`AUTH_CODE_TTL_SECS`); expired codes and refresh tokens are pruned on insert. Refresh tokens are issued when scope includes `offline_access`; expiries are configurable per server.
  - `src-tauri/src/cimd.rs` / `src-tauri/src/dcr.rs` — Pure client-registration logic: URL classification, document fetch, validation and cache for Client ID Metadata Documents; RFC 7591 metadata validation (`validate_registration`, errors carry `invalid_redirect_uri` or `invalid_client_metadata`). Both have exhaustive unit tests.
  - `src-tauri/src/mcp.rs` — Pure MCP protocol logic for `/mcp`: `handle_message(message, McpContext)` returns `Outcome::Reply` (JSON-RPC response) or `Outcome::Accepted` (notification, HTTP 202). Methods `initialize` (versions 2025-11-25, 2025-06-18, 2025-03-26), `ping`, `tools/list`, `tools/call` with tools `whoami` (the `/resource` JSON) and `echo`; also `origin_allowed()` and `is_supported_version()`.
  - `src-tauri/src/mcp_probe.rs` — Client-side MCP probe behind `probe_mcp(id, access_token)`: POSTs `initialize`, `notifications/initialized`, `tools/list` to the config's MCP URL with the bearer token, the negotiated `MCP-Protocol-Version` and any `Mcp-Session-Id`, and returns a `ProbeReport` of `ProbeStep`s (stops at the first failure; a 401 adds a discovery hint from the challenge). `sse_message_for_id()` extracts the matching JSON-RPC message from `text/event-stream` responses.
  - `src-tauri/src/discovery.rs` — Metadata discovery behind `fetch_server_metadata(issuer_url, resource_url, resource_kind)`. With a URL it follows the MCP authorization order: an unauthenticated probe (GET for `ResourceKind::Resource`, an MCP `initialize` POST for `ResourceKind::Mcp`), its 401 `WWW-Authenticate` `resource_metadata` (strict: only that URL is tried) and `scope`, else the RFC 9728 well-known URLs (path-insertion, then root); checks the PRM `resource` matches the resource URL; takes `authorization_servers[0]`; then tries RFC 8414, OIDC path-insertion, and OIDC path-appended metadata URLs for the issuer (the issuer-only fetch uses the same AS fallback). Returns `ServerMetadataResponse` (incl. discovered `issuer_url`, `challenge_scope`, and `scopes_supported` chosen challenge > PRM > AS) or `DiscoveryFailure`; both carry a `trace` of `DiscoveryStep`s (URL, status with 0 meaning no response, outcome). `parse_www_authenticate()` is the pure header parser. The response also carries `registration_endpoint`, `client_id_metadata_document_supported` and `token_endpoint_auth_methods_supported`.
  - `src-tauri/src/client_registration.rs` — Client-side registration: `RegistrationMode` / `TokenAuthMethod` enums (stored as text, exported to TypeScript), `credential_style` and `client_credentials` (what a token request sends), `client_metadata_document` (the CIMD document generated from a config; `ui/src/lib/clientMetadataDocument.fixtures.json` pins it against the TypeScript generator), `registration_request` / `register_client` (RFC 7591 POST; any HTTP answer is returned as an `AuthResponse`), and `verify_client_document` (reuses `cimd::fetch_document` / `parse_metadata` / `check_redirect_uri` and requires this app's callback URL in `redirect_uris`; a document served locally is generated instead of fetched). End-to-end tests in `oauth_server.rs` run the client request builders against the app's own server router.
  - `src-tauri/src/auth_client.rs` — Client-side OAuth flow execution: `client_credentials`, `authorization_code` (browser flow with PKCE S256, fixed callback port 5757, 5-minute timeout, cancellable), and `refresh_token`. `lookup_config()` returns a `ResolvedClientConfig` struct with the JSON param blobs already parsed. The callback handler only enforces the `state` check when the state param was actually sent (it can be disabled for diagnostics). `open_browser()` tries Chrome (per-OS paths, isolated profile, devtools) and falls back to the OS default browser. The Chrome process is watched: if it exits (after a 3-second window that filters out handoffs to an already-running instance of the same profile), the flow fails with "Browser closed before authorization completed". A callback that arrives first wins, and the fallback browser is not tracked. Refresh tokens in token responses are persisted automatically; rotation is supported. A config has separate `resource_url` (used by `call_resource`) and `mcp_url` (used by `probe_mcp`). `ResolvedClientConfig::token_resource` picks the one tokens are requested for (the only one set, or `mcp_url` when both are set and `token_for_mcp` is on), and `resource=<url>` is sent as a default param on the authorize, token, client_credentials, and refresh requests, toggled by the `resource` checkbox in each param section (stored in the same disabled maps as the other params); a `resource` extra param replaces it. `call_resource` GETs the resource URL with an `Authorization: Bearer` token and returns an `AuthResponse`. Credentials are decided by `client_registration::credential_style(mode, token_auth_method)`: preregistered sends `client_id` + `client_secret` in the body, CIMD and DCR `none` are public (`client_id` only, no secret), DCR `client_secret_basic` uses an `Authorization: Basic` header; unchecked params still apply, and an extra param named `client_secret` can force a secret for diagnostics (refresh requests send no extras). `post_token_request` and `code_exchange_request` are the shared token-request pieces. For a CIMD config with `serve_client_metadata`, `create` and `update` store the local document URL as the client ID, and the callback listener (`callback_router`) also serves the generated document at `GET /client-metadata/<config id>` (`application/json`, `no-store`) and stays up until the token exchange has finished, because the server may re-fetch the document at the token endpoint. Token requests outside that flow (`post_with_local_document`) bind the callback port just for the request, for the same reason.
  - `src-tauri/permissions/default.toml` — Tauri 2 command permissions. Every command needs an `allow-*` entry here and in the `default` set, or it is silently blocked.
- `ui/` — TypeScript + React 19 frontend built with Vite (`vite.config.ts`, `tsconfig.json` with `strict` and `noUncheckedIndexedAccess`). `npm run build` writes `ui/dist/` (gitignored): `index.html`, bundled JS/CSS, and `fonts/` copied from `ui/public/fonts/`. JetBrains Mono is bundled locally; there are no network fonts — the CSP in `tauri.conf.json` only allows `'self'` plus the Tauri IPC origin (`devCsp` additionally allows the Vite dev server for HMR).
  - `ui/src/main.tsx` — entry point. Mounts `<App />` in `StrictMode`, then runs the update check.
  - `ui/src/App.tsx` — split layout with independent left (servers) and right (client configs) page states, panel collapse toggles, and the dismissible error banner. Owns the list UI hooks so their state survives while a form replaces a list.
  - `ui/src/state.tsx` — `AppStateProvider` context: servers, client configs, callback URL, last error, the most recent `/resource` access per server, and the last five client metadata fetches per server. Subscribes to the `resource-access` and `client-metadata-fetched` events (dropping entries for deleted servers) and to `server-users-changed` and `server-clients-changed` (reload servers when a user or client registers).
  - `ui/src/api.ts` — `createApi()` wraps the generated `commands.*`. It unwraps `{ status }` results, reports list and mutation failures to the error banner as `<command_name>: <error>`, and reloads the affected list after a successful mutation. Auth, refresh, resource-call, registration (`registerClient`, whose RFC 7591 error bodies arrive as responses), document-verification (`VerifyOutcome`, a list of pass/fail checks), and metadata failures are returned as outcomes (a metadata failure also carries the discovery trace; `fetch_server_metadata` is the one command whose error type is a struct, `DiscoveryFailure`, so `CommandResult` takes an error type parameter) and shown next to the config that requested them.
  - `ui/src/bindings.ts` — generated by tauri-specta. Do not edit by hand.
  - `ui/src/hooks/useServerListUi.ts`, `ui/src/hooks/useClientConfigListUi.ts` — list UI state (the newest access token per config survives later failures, and a new token clears resource and probe results; search text, which cards are expanded — cards start collapsed to just their name — expanded sections, per-config auth, resource-call, metadata and document-verification state, settings edits, add-user drafts and per-user edits with a saved flash).
  - `ui/src/components/` — React components: `ServerList` (server cards show the issuer, authorization and token URLs the saved settings advertise via `lib/serverUrls.ts`, plus a "Local URL" when a public URL is set, and imported clients use those URLs; an "MCP" section with the URL, the `claude mcp add` command and Copy buttons when MCP is enabled, the last `/resource` or `/mcp` access with its path, show a "Client metadata fetches" section and a `dynamic` badge with name, auth method and redirect URIs on dynamically registered clients; CIMD clients are not stored, so they appear only in the fetch list), `ServerForm`, `ServerSettingsForm`, `ClientConfigList` (Call Resource appears with a resource URL, and an "MCP Probe" button with an MCP URL shows the probe steps as `ProbeStateView`), `ClientConfigForm` (each filled resource or MCP URL offers "Discover OAuth from this URL", which turns on server metadata and makes the issuer read-only; with both URLs a select picks which one tokens are for; its "Pull Now" button fetches metadata into the form early, starting from the ticked URL, else the resource URL, the MCP URL, then the issuer; a save fetches only if none was pulled for the current issuer and resource URL; the discovery trace shows under the error banner), `RegistrationFields` (registration mode, client ID/secret, the CIMD document with Copy, "Serve document locally" (on when CIMD is chosen; the client ID is then read-only), and the DCR auth method and Register button; the secret input is disabled for public clients and Register fills the form from a 200/201 response), `ClientMetadataDocumentView`, `AuthResults` (incl. `VerifyStateView`), `ToggleSection`, `HelpTip` (the ⓘ field-help icon; its tooltip is portaled to `document.body` with fixed positioning so panels cannot clip it), plus `shared` helpers. `FormInput`, `Detail`, and `FieldLabel` take an optional `help` key.

**Adding a backend command:**

1. Add a `#[tauri::command]` function with `#[specta::specta]` in the relevant module. Any new DTO the frontend receives or sends derives `specta::Type`.
2. Add the function to `collect_commands!` in `specta_builder()` in `lib.rs`.
3. Add an `allow-*` permission in `src-tauri/permissions/default.toml` and list it in the `default` set.
4. Regenerate the bindings: run `cargo tauri dev` (debug builds write `ui/src/bindings.ts`) or `UPDATE_BINDINGS=1 cargo test bindings_are_current` from `src-tauri/`.
5. Call it as `commands.<camelCaseName>` from `ui/src/api.ts`, using the existing `reported`/`mutate`/`unreported` helpers for error handling.

**Frontend serves from** `ui/dist/` (configured as `frontendDist` in `tauri.conf.json`). The dev server is `http://localhost:5173` (`devUrl`); `beforeDevCommand` and `beforeBuildCommand` run the `ui/` npm scripts. Both set `cwd` to `../ui` (relative to `src-tauri/`) because the repo has more than one `package.json`, and Tauri's own lookup can pick `site/`.

## Key Conventions

- Strict TypeScript with React 19 and no state library: component state lives in hooks and components, and shared app state lives in the single `AppStateProvider` context.
- Model UI state as discriminated unions (`CommandResult`, `AuthOutcome`, `MetadataOutcome`, the page states in `App.tsx`) and handle every variant in exhaustive `switch` statements.
- The generated `ui/src/bindings.ts` is the Rust↔TypeScript contract. Do not hand-write DTO types that duplicate Rust structs.
- IDs are integers everywhere (Rust `i64`, TypeScript `number`, JSON numbers). Specta casts `i64` to `number` (see `dangerously_cast_bigints_to_number` in `lib.rs`), which is safe for SQLite row IDs and token expiries.
- Param maps are `Record`s in TypeScript and JSON-text columns in SQLite. They are parsed and serialized only in `ui/src/lib/convert.ts`.
- Backend is minimal Rust with Tauri plugins; command errors are `Result<_, String>` and must reach the UI (`api.ts` forwards them to the error banner, except auth, refresh, resource-call, and metadata failures, which are shown with their config).
- Dark theme UI with CSS variables, JetBrains Mono font (bundled in `ui/public/fonts/`).
- Cargo commands must be run from `src-tauri/` or use `cargo tauri` from root. npm commands must be run from `ui/`.
